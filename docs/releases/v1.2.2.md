# Auto-Subtitle-Generator v1.2.2 — Symlink-Safe Sidecar Writes + Dependency Refresh

## Release Summary

v1.2.2 is a security hardening and maintenance release. It closes a
medium-severity filesystem vulnerability in which every sidecar the pipeline
writes next to the input video could be redirected through a planted symbolic
link and used to overwrite arbitrary files the running user can write. It also
moves the ML stack to PyTorch 2.14 (cu132), patches a path-traversal advisory
in `accelerate`, and refreshes every product, developer, and CI/CD dependency
to its latest final version. There are no intended changes to normal-path
behaviour, CLI flags, or configuration, and output filenames are unchanged;
the one deliberate behaviour change is that symlinked outputs, tampered
scratch entries, and symlinked resume audio are now rejected.

## Security Fix

### Symlink following in the input video directory (MEDIUM)

The subtitle pipeline writes several files beside the user-supplied video
using ordinary `open(..., "w")` and FFmpeg `-y`. Both follow symbolic links.
An attacker who controls a directory the victim later processes (a shared
folder, a zip of "videos to subtitle", a USB drop) could plant symlinks with
the pipeline's predictable sidecar names — `movie.common_input.json`,
`movie.manifest.json`, `movie.en.srt.tmp`, `movie_temp.wav`,
`movie_multilang.mp4` — pointing at `~/.ssh/authorized_keys`, shell rc files,
or application configs. Processing that folder truncated and replaced the
target with JSON, SRT, WAV, or MP4 bytes.

**Affected write sites (all fixed):**

- `modules/subtitles/srt_io.py` — `save_srt` / `save_translated_srt` wrote to
  a predictable `<srt>.tmp` before `os.replace`.
- `modules/pipeline/translation.py` — `*.common_input.json`,
  `*.manifest.json`, and `*.pivot_pivoted.json`.
- `auto_subtitle.py` — `*.source_lang.txt` resume sidecar and the final
  `_multilang` mux output.
- `modules/media/ffmpeg_utils.py` — `*_temp.wav` extraction target.

### Remediation: `modules/safe_io.py`

A new stdlib-only module centralises every sidecar write around a
`ScratchReservation`:

- `reserve_temp_path(final_path)` creates a private `0700` directory with an
  unpredictable name beside the destination and an exclusively created file
  inside it (`os.open(O_CREAT | O_EXCL | O_NOFOLLOW, 0o666)`, so the process
  umask is applied at creation and never modified), and records the
  device/inode identity of both. The final extension is preserved so FFmpeg
  still selects the correct muxer; callers pass `reservation.path` to FFmpeg.
- `atomic_text_writer(path)` reserves the same way and writes **through the
  creation descriptor** — the scratch pathname is never reopened.
- `promote_temp_path(reservation, final_path)` refuses a symlink destination,
  re-verifies both identities, then moves the file. On POSIX the move is a
  `renameat` bound to the held directory descriptor, so renaming the scratch
  directory cannot redirect it; elsewhere `os.replace` runs only after the
  identity check. A replaced directory or file raises `SymlinkRefusedError`
  and leaves the reservation intact for `discard_temp_path`.
- `discard_temp_path(reservation)` unlinks through the held directory
  descriptor (or after re-verifying identities) and removes the private
  directory with `rmdir` only — it never recurses, so a planted directory or
  Windows junction carrying a scratch-looking name is never walked.
- Scratch names use the opaque prefix `.asg-tmp-<stem[:24]>-<sha256[:8]>-`,
  so long basenames cannot hit `ENAMETOOLONG` and distinct owners cannot
  collide. `cleanup_temp_files` deliberately does **not** match scratch
  entries: they are owned and removed by their reservation (including on
  `subprocess.TimeoutExpired` via `finally`), and the per-video scan must
  never `rmtree` anything found in the untrusted input folder.
- `embed_subtitles` reserves its scratch path inside its error handler, so a
  read-only or full input directory still yields the established logged
  `None` result instead of an exception.

Additional hardening in the same pass:

- Resume no longer reuses a `*_temp.wav` that is a symbolic link.
- `_write_recorded_source_language` now logs a warning on failure instead of
  silently swallowing the `OSError`.
- The now-unused `_cleanup_temp_audio_retry` helper was removed from
  `modules/media/ffmpeg_utils.py`.

Remaining reads of attacker-controlled sidecars (resume SRTs, pivot SRTs)
are unchanged: they only read, and their content is validated by the existing
SRT guard before use.

## Dependency & Toolchain Refresh

Every production, ML, developer, and CI/CD dependency was audited against its
upstream registry and moved to the latest final (non-pre-release) version the
resolver accepts.

### 🔒 `accelerate` PYSEC-2026-3804 (path traversal / DoS)

`pip-audit` flagged `accelerate` 1.14.0: `load_checkpoint_in_model` and
`load_checkpoint_and_dispatch` did not sanitise `weight_map` entries from
sharded checkpoint indexes, allowing `../` / absolute paths to read arbitrary
files or named pipes to block indefinitely. The advisory covers releases
*through* 1.14.0; `accelerate` is now `^1.15.0`, which is outside the affected
range. The local gate and CI fail on this advisory until the bump is applied.

### 📦 ML / Runtime Dependencies

- `torch` `2.13.0+cu132` → `2.14.0+cu132` (Linux/Windows) and `>=2.14,<2.15`
  (macOS, PyPI). `torch` 2.14.0 is now a final release on both PyPI and the
  cu132 index; it was pre-final (CUDA index only) when v1.2.1 shipped.
- `torchvision` `0.28.0+cu132` → `0.29.0+cu132` and `>=0.29,<0.30` (macOS).
- `nvidia-cudnn-cu13` `9.20.0.48` → `9.24.0.43` — dictated by the
  `torch 2.14.0+cu132` wheel metadata, not chosen here.
- `nvidia-cublas` stays at `13.4.0.1`: `torch 2.14.0+cu132` still pins
  `cuda-toolkit 13.2.1`, which pins `nvidia-cublas ==13.4.0.1.*`.
- `transformers` `^5.16.1` → `^5.17.0`
- `accelerate` `^1.14.0` → `^1.15.0` (security, see above)
- `faster-whisper`, `sentencepiece`, `audioread`, and `pyyaml` were already at
  their latest published versions and are unchanged.

### Lock-file note

Re-locking with the v1.2.1 `torch >=2.13,<2.14` macOS range failed version
solving after ~7 minutes (`nvidia-cublas` conflict between PyPI `torch`'s
`cuda-toolkit 13.0.3` and the cu132 wheel's `13.2.1`). Moving both `torch`
branches to 2.14 resolves it and the lock now completes in ~6 seconds; the
stale `cuda-toolkit 13.0.3` entry is gone from `poetry.lock`.

### Still deferred: CUDA 13.4 (`cu134`)

There is still no stable `cu134` index on `download.pytorch.org`; the project
stays on `cu132`. Revisit when PyTorch promotes `cu134` to the stable channel.

### Still deferred: `audio-separator` 0.47.0 / `librosa` 1.0

Retried with the new `torch` 2.14 pins under a 5-minute bound: the resolver
still thrashes without completing, exactly as documented in v1.2.1
(`Duplicate dependencies for nvidia-cublas` via the darwin/arm64
`torch>=2.13` marker). `audio-separator` stays at `^0.44.5` and `librosa`
keeps its `>=0.10.2,<1.0` ceiling.

## Tests

- New `tests/modules/test_safe_io.py` reproduces the original proof of
  concept: symlinks are planted at `movie.common_input.json`,
  `movie.en.srt.tmp`, and `movie_temp.wav` pointing at a victim file, and the
  suite asserts the victim is untouched — writes are either refused or land
  on the real name beside the link. It also covers the live-attacker variants
  (scratch directory renamed away and replaced by a symlink during a write;
  replaced by a plain directory + regular file before promotion; replaced
  before discard, where the bystander directory must survive), umask
  preservation, bounded collision-resistant tags for 240-character
  basenames, cleanup never touching scratch-named directories, and scratch
  discard on `ffprobe` timeout. Symlink fixtures skip on Windows hosts that
  refuse symlink creation.
- Existing unit tests that mocked `builtins.open` / `os.replace` were
  repointed at the new `safe_io` seams (`atomic_text_writer`,
  `reserve_temp_path`, `promote_temp_path`, `discard_temp_path`) so they no
  longer create stray files in the working directory.
- `embed_subtitles` tests now assert FFmpeg is pointed at the reserved scratch
  path and that the result is promoted to `_multilang`.

# Auto-Subtitle-Generator v1.2.4 — Symlink-Safe Input Collection & Descriptor-Bound Inputs

## Release Summary

v1.2.4 is a security release. It closes a MEDIUM-severity finding from a
vulnerability scan: a symbolic link planted in an untrusted input folder could
make the pipeline read a private video from elsewhere on the victim's machine
and copy it, with a transcript, into that folder. v1.2.2 hardened every file
the pipeline *writes* against planted links; this release applies the same
discipline to the files it *reads*.

The fix has two layers. Collection refuses links and anything that resolves
outside the selected folder, and a new `modules/media/input_binding.py` keeps
the validated file open for the whole run and hands FFprobe/FFmpeg that open
file rather than its name, so a link or directory swapped in after validation
changes nothing. Review follow-ups from CodeRabbit and Copilot extended the
binding to the directory chain, the resume decision, the batch summary, and
the Windows fallback.

There are no changes to CLI flags, configuration, or deliverable names.

## The Finding

> Folder scans follow planted video symlinks and copy victim-owned media into
> the attacker directory. (MEDIUM, code-traced)

`collect_video_files()` in `modules/media/file_utils.py` treated any directory
entry whose extension was in `config.VIDEO_EXTENSIONS` as an input.
`os.path.isfile()` and FFmpeg `-i` both follow symbolic links, and output
paths were derived from `os.path.dirname(video_path)` — the folder holding
the *link* — not from `os.path.realpath()`.

Attack path:

1. The attacker can place files in a folder the victim will process (USB
   drop, zip of clips, shared incoming directory) and can create symlinks.
1. They plant `vacation.mp4 → C:\Users\<user>\Videos\private.mp4` (or
   `~/Videos/...`) next to one real decoy clip.
1. The victim uses the documented drag-and-drop / folder flow.
   `collect_video_files()` includes the link; `process_video()` sets `folder`
   to the attacker directory.
1. FFmpeg `-i` follows the link. Audio extraction transcribes the private
   video; the final `-c:v copy -c:a copy` mux writes a full duplicate as
   `vacation_multilang.mp4` beside the link, with SRT sidecars.

A local proof of concept with a dummy victim MP4 and a planted link
reproduced the copy.

## Layer 1 — Collection refuses links (`modules/media/file_utils.py`)

- A top-level input path that is itself a symlink or Windows junction is
  skipped (`is_link()` checks both `os.path.islink` and
  `os.path.isjunction`).
- The walk runs with `followlinks=False`, and linked directories are pruned
  from `dir_names` explicitly — `os.walk` never descends into symlinked
  directories, but junctions are not symlinks to it.
- `_is_safe_input_file()` accepts only a regular file (`os.lstat` →
  `S_ISREG`) whose `os.path.realpath()` stays inside the `realpath` of the
  selected folder (`os.path.commonpath`).
- Every rejection is logged at `WARNING` with the reason, so a user who
  legitimately symlinked their own clip sees why it was skipped instead of
  losing it silently.

## Layer 2 — Descriptor-bound inputs (`modules/media/input_binding.py`, new)

### Why a pathname check is not enough

Collection happens before AI initialisation. Model loading can take minutes,
and only then do FFprobe and FFmpeg open the input by pathname. A party with
concurrent write access to the input folder can replace the validated regular
file — or any parent directory below the selected folder — with a link in that
window. Revalidating the pathname before each open does not close the race.

### Mechanism

`bind_input(path)` is a context manager held by `process_video()` around the
whole pipeline and by `_process_batch_video()` around the batch item
(nested binds share the outer binding):

- **Trusted root**: `get_input_files()` calls `set_input_root()` with the
  selected folder. The pathname form is kept to match collected paths; the
  `realpath` taken at selection time is what gets opened, so a folder the
  user selected *through* a symlink still works while a link planted at the
  root afterwards is refused.
- **POSIX**: the root is opened with `O_DIRECTORY | O_NOFOLLOW`; each
  directory component below it is opened relative to the previous descriptor
  with `O_NOFOLLOW` (`ENOTDIR`/`ELOOP` → `InputRefusedError: directory 'clips' was replaced by a link`); the file is opened with
  `O_RDONLY | O_NOFOLLOW | O_CLOEXEC`; `fstat` must report a regular file.
  Containment is decided with `os.path.commonpath` and `relpath` components,
  so a child named `..clips` is not mistaken for a parent reference.
- **Consumption**: `media_source(path)` looks the binding up by pathname and
  returns `("/dev/fd/N", (N,))`; `get_audio_duration`, `extract_clean_audio`
  and `run_ffmpeg_progress` pass the fd to the child via `pass_fds`.
  `/dev/fd/N` may share the file offset with our descriptor (macOS `dup`
  semantics), so `rewind_inputs()` runs immediately before *every* spawn —
  not once when the source is captured — because a probe can run between
  capture and launch.
- **Windows**: no `O_NOFOLLOW`, no fd passing, and a held file handle pins
  only the file, not the directory chain FFmpeg walks by pathname. Each
  component below the root is checked with `is_link`, the file is opened
  after an `lstat` check and `fstat` identity is compared, then the bytes are
  copied *from that handle* with `shutil.copyfileobj` into
  `tempfile.mkdtemp()` under the user's `%TEMP%`. A copy directory inside the
  input tree would not be a boundary — the folder's owner can list its random
  name and re-create it under a swapped parent — so the copy lives where they
  cannot write. FFmpeg reads the copy; it is removed on close. This costs a
  full copy of each input on Windows; a native handle-relative
  (`NtCreateFile`) chain was rejected because CI is Linux-only and it would
  ship untested.
- **Resume decision**: `process_video` binds *before*
  `workdir.bind_work_dir_to_source`, and `source_stamp()` reads through
  `stat_input()` (fstat of the bound descriptor). The stamp now records
  `device` and `inode` as well as `size` and `mtime_ns`, so a same-size,
  same-mtime replacement cannot reuse the previous input's artifacts.
- **Batch summary**: `_process_batch_video` holds a non-strict outer binding;
  if it is refused, `build_file_summary(..., probe=False)` reports `N/A`
  without handing the rejected pathname to FFprobe.

The lookup-by-pathname design (`_active_bindings`, a module-level registry)
was chosen so the pipeline's string-based call chain
(`transcribe_video_audio`, `extract_clean_audio`, `embed_subtitles`, …) keeps
its signatures. It is single-video-at-a-time state; processing the same path
concurrently in one process is unsupported.

### Verification with real FFmpeg

On Linux, with a 2.0 s `real.mp4` bound and a 3.0 s `secret.mp4` as the
victim:

| Scenario | Bound probe / extract / mux | Bare pathname probe |
| --- | --- | --- |
| `real.mp4` replaced by a symlink to `secret.mp4` mid-run | 2.0 s | 3.0 s |
| Parent `clips/` renamed and replaced by a link to a victim directory | refused at bind | 3.0 s |
| Same, Windows fallback forced, victim link planted at the copy's relative path | 2.0 s (copy in `$TMPDIR`) | 3.0 s |

## Upgrade Notes

- A symlinked clip in the input folder is now skipped with a warning instead
  of processed. Point the tool at the real file or folder.
- The work-directory stamp format changed; a `<base>.asg-temp/` left by an
  interrupted v1.2.3 run reads as `BIND_CHANGED` once and is discarded, so
  that video starts from scratch.
- Windows only: each input is copied to `%TEMP%` for the duration of its run.
  The temp drive needs free space equal to the largest input; set `TEMP` to
  redirect it. A dedicated configuration key is a possible follow-up.

## Known Limitations

- Hard links are indistinguishable from regular files and are not detected;
  creating one requires access to the victim file on the same filesystem,
  which is outside this threat model.
- FFmpeg receives `/dev/fd/N` with no extension, so the input container is
  detected by content probing rather than suffix. Output format and subtitle
  codec selection still use the original filename's extension.

## Breaking Changes

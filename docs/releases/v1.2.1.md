# Auto-Subtitle-Generator v1.2.1 — Dependency & Toolchain Refresh

## Release Summary

v1.2.1 is a maintenance release. Every production, ML, developer, and CI/CD
dependency was audited against its upstream registry and moved to the latest
final (non-pre-release) version that the resolver accepts. No application
behaviour changes; no public API changes.

Two upgrades were evaluated and deliberately **deferred**, each with blocking
evidence recorded below: CUDA 13.3.1, and `audio-separator` 0.47.0.

## Deferred: CUDA 13.3.1

CUDA Toolkit 13.3.1 has been released by NVIDIA, but **PyTorch never published
a `cu133` build and has skipped the version entirely.** Probing the wheel
indexes directly:

| Variant | stable | nightly |
| ------- | ------ | ------- |
| `cu130` | 200 | 200 |
| `cu131` | 403 | 403 |
| `cu132` | 200 | 200 |
| `cu133` | 403 | 403 |
| `cu134` | 403 | 200 |

There is no `cu133` artifact to upgrade *to* — on either channel. PyTorch's
next CUDA target is **13.4**, currently nightly-only. Pinning `cu133` would
break every GPU install.

Two further constraints reinforce holding at `cu132`:

- `torch 2.13.0+cu132` hard-pins the CUDA 13.2.1 component stack — it depends
  on `cuda-toolkit[cublas,cudart,...] (13.2.1)`, which pins
  `nvidia-cublas (==13.4.0.1.*)`, and it separately pins
  `nvidia-cudnn-cu13 (9.20.0.48)`. Raising either to its current PyPI release
  (`13.6.1.10` / `9.25.1.1`) fails version solving outright. Both pins are
  retained deliberately: they are dictated by `torch`, not chosen here.
- The latest final `torch` is `2.13.0` on both PyPI and the `pytorch/pytorch`
  GitHub releases. `torch 2.14.0+cu132` / `torchvision 0.29.0+cu132` wheels are
  staged on the CUDA index but are absent from PyPI with no upstream release,
  so they are pre-final; adopting them would also desync the macOS branch,
  which resolves from PyPI. `torch` / `torchvision` therefore remain at
  `2.13.0` / `0.28.0`.

**Follow-up:** revisit when PyTorch promotes `cu134` to the stable channel.

## Deferred: audio-separator 0.47.0

`audio-separator` 0.47.0 (with `librosa` `^1.0.0`) was prepared and then
reverted. It makes Poetry's resolver blow up combinatorially: the lock never
completes, with runs observed at 8, 30, and 150+ minutes of saturated CPU
against a config that otherwise locks in ~11 seconds.

The trigger was isolated by bisection — 0.47.0 alone reproduces it with
`librosa` held at `<1.0`, so `librosa` is not implicated. Verbose resolver
output points at `Duplicate dependencies for nvidia-cublas`: 0.47.0 adds
`torch<3,>=2.13` under a `sys_platform == "darwin" and platform_machine == "arm64"` marker, which pulls in the **PyPI** `torch 2.13.0`. That wheel depends
on `cuda-toolkit (13.0.3)` — a different CUDA component set than the cu132
wheel's `13.2.1` — leaving two irreconcilable `nvidia-cublas` constraints for
the solver to thrash between. Pinning the Darwin `torch`/`torchvision` exactly,
and removing the project's own `nvidia-*` pins, were both tried and neither
resolved it.

`audio-separator` therefore stays at `^0.44.5`, and `librosa` keeps its
`>=0.10.2,<1.0` ceiling (0.44.5 calls `librosa.get_duration(filename=...)`,
an argument removed in librosa 1.0). Worth noting for the follow-up: 0.47.0
itself is compatible with librosa 1.0 — it calls `get_duration(path=...)` —
so once the resolver conflict is solved both can move together.

Security release. A video file dropped into the input folder is now only ever
read if it is a plain regular file inside the folder you selected, and the
pipeline keeps that exact file open for the whole run, so a symlink, junction
or swapped directory planted in the input folder can no longer make the
pipeline read — and copy out — media from somewhere else on your machine. No
changes to CLI flags, configuration, or deliverable filenames.

## 🔒 Planted symlinks can no longer exfiltrate your videos

`collect_video_files()` accepted any directory entry with a video extension.
`os.path.isfile()` and FFmpeg `-i` both follow symbolic links, and outputs are
written next to the *link*, so a `vacation.mp4 → ~/Videos/private.mp4`
symlink planted in an untrusted folder (a USB stick, a shared "incoming"
directory, a zip of clips) caused the linked private video to be transcribed
and stream-copied into that folder as `vacation_multilang.mp4` plus SRT
sidecars. Sidecar *writes* were hardened in v1.2.2; input *reads* were not.

Collection now skips a top-level symlink or junction, never descends into a
linked directory, and accepts only regular files whose real path stays inside
the selected folder. Every rejection is logged at `WARNING` with the reason.

## 🧷 The file you validated is the file FFmpeg reads

A pathname check alone leaves a window: model loading can take minutes, and a
party with write access to the input folder could swap the validated file, or
one of its parent directories, for a link before FFprobe/FFmpeg open it. The
new `modules/media/input_binding.py` closes that:

- **Linux / macOS**: the selected folder is opened as a descriptor, every
  directory component below it and the file itself are opened relative to the
  previous descriptor with `O_NOFOLLOW`, `fstat` confirms a regular file, and
  FFprobe/FFmpeg receive `/dev/fd/N` for that exact open file through
  duration probing, audio extraction and the final mux.
- **Windows**: there is no `O_NOFOLLOW` and no descriptor passing, and a held
  file handle does not pin the directory chain FFmpeg walks by pathname. The
  bytes are copied *from the validated handle* into a private directory under
  your `%TEMP%`, which the input folder's owner cannot modify, and FFmpeg reads
  that copy. The copy is removed when the video finishes.

Verified with real FFmpeg: after replacing the pathname (and, separately, its
parent directory) with a link to a different video mid-run, probing, audio
extraction and the `-c copy` mux all still produced the originally opened
file; the same probe on the bare pathname returned the substituted one.

The resume decision is made *after* binding and the work-directory stamp now
records device and inode alongside size and mtime, taken from the bound
descriptor, so a same-name replacement can never reuse the previous input's
extracted audio or subtitles.

## ⬆️ Upgrade notes

- A symlinked clip in the input folder is now **skipped with a warning**
  instead of processed. Point the tool at the real file or folder.
- The work-directory stamp format changed; a `<base>.asg-temp/` left by an
  interrupted v1.2.3 run is discarded once on first use, and that video starts
  from scratch.
- **Windows only**: each input is copied to `%TEMP%` for the duration of its
  run, so that drive needs free space equal to the largest input. Set `TEMP`
  to redirect it.

## Breaking changes

- None. CLI flags, configuration keys and deliverable names are unchanged.
